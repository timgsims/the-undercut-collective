## What this project is

A private F1 Fantasy dashboard for Tim's 8-person league (F1 Fantasy is the
official Formula 1 game). It's a static site (`index.html`) generated by a
Python script and hosted on GitHub Pages at `f1fantasy.simsey.co.nz`. There
is **no manual data entry** — an automated pipeline pulls everything from F1
Fantasy's own (undocumented) web API into a local SQLite database, and the
dashboard is generated from that.

This replaced an earlier Excel-workbook-based version entirely. If you find
any reference to `.xlsx` files or `read_workbook()` anywhere, it's stale —
ignore it. The `.xlsx` files still sitting in the repo folder are leftover
artifacts from that era, untracked in git, and not used by anything.

## Architecture

```
fetch_f1_data.py  →  f1_data.db (SQLite, gitignored)  →  build_dashboard.py  →  index.html  →  git push  →  GitHub Pages
```

- **`fetch_f1_data.py`** — hits F1 Fantasy's API (session-cookie-gated
  "services" endpoints for personal/opponent team data, plus a few fully
  public no-auth "feeds" endpoints for driver data and country leaderboards)
  and writes into `f1_data.db`. Cookie lives at `secrets/f1_cookie.txt`
  (gitignored, never paste the real cookie into chat).
- **`build_dashboard.py`** — reads `f1_data.db`, computes everything
  (standings, podiums, budgets, chips, etc.), and renders the whole site as
  one `index.html` with client-side tab switching (no server-side routing).
  Running it directly (`python build_dashboard.py`) also auto-commits and
  pushes `index.html` to GitHub (see `git_push()` near the bottom of the
  file — set `GITHUB_REMOTE = ""` there to disable auto-push).
- **`manifest.json` + `sw.js` + `icons/`** — PWA setup so "Add to Home
  Screen" (iOS Safari) / "Install app" (Android Chrome) works as a real
  standalone app icon, not a browser bookmark. `sw.js` is network-first
  (never serves stale content while online — only used as an offline
  fallback), which is also what satisfies Chrome's installability
  requirement for a registered service worker.
- **`gate_check.py` + `run_pipeline.sh`** — the automated pipeline that runs
  on the sentinel server (see below).

  either write a real `ALTER TABLE` migration or manually delete
  `f1_data.db` and let it rebuild from a fresh fetch — but doing the latter
  on a machine where fetch might partially fail (e.g. a transient network
  blip on one manager) means that manager's *entire* history gets silently
  dropped for that rebuild, since there's no prior data to fall back on.
  This has actually happened (Tim's score got wiped once). If you must wipe
  a DB, verify row counts per manager afterward before trusting it.

## Data model (SQLite, `f1_data.db`)

Key tables: `managers`, `players` (drivers + constructors), `player_results`
(per round: `gameday_points`, `overall_points`, `value_change`, `value`),
`player_session_points`, `session_status`, `race_results` (per manager per
round: `points`, `season_total`, `team_value`, `team_balance`,
`captain_player_id`, `is_final`, `gameday_rank`, `overall_rank`,
`transfers_made`, `inactive_driver_penalty`), `team_picks`, `chips_used`,
`races`, `nz_leaderboard`, `round_finalized_at`.

### Non-obvious data quirks (all confirmed against real API responses / Tim's own memory — don't re-derive these from scratch)

- **`mds` field = match-day status.** 1/2 = live/partial, 3 = fully
  finalized. This is the *only* signal that gates whether a race result
  (podium, finish position, winner) can be declared. Season totals/points
  progression are live-inclusive (update mid-race); podiums/finish
  positions are not — they wait for `mds==3`. This correctly and elegantly
  handles sprint weekends too, no external schedule data needed.
- **One-round lag on budget/value fields.** F1's API reports team budget
  and player price as of the *start* of the round you're querying, i.e. one
  round behind. To get "value after round N", you peek at round N+1's raw
  data. This is used for team budget (`race_results.team_value`) and player
  price (`player_results.value`, `value_change`). For the *current*
  in-progress round there's no N+1 data yet — code falls back to that
  round's own (lagged) raw figure rather than showing blank, except for
  *price change*, which genuinely can't be computed without the next
  round's data and is correctly left blank until it exists.
- **Wildcard's round-taken field is broken.** `wildcardtakengd` always
  returns 0 from F1's API. The *real* field is `is_wildcard_taken_gd_id`
  (undocumented, found by manual API inspection), confirmed stable across
  every subsequent round's snapshot and verified against Tim's own memory
  (his Wildcard was round 5/Canada, not round 6/Monaco as originally
  assumed from a stale-data artifact). All other chips' `*takengd` fields
  work correctly and don't need this workaround.
- **Ties are real ties.** F1 Fantasy's own T&Cs confirm tiebreakers only
  apply to end-of-season prizes, not per-race display — so a tied race
  shows both managers as e.g. "1st", never arbitrarily resolved. Standard
  competition ranking (ties share a rank, next rank skips by tie-count) is
  implemented once in `rank_with_ties()` and reused everywhere, specifically
  to avoid the "same stat recomputed slightly differently in different
  panels" bug class that came up repeatedly before that consolidation.
- **NZ leaderboard is inherently incomplete.** The only public, unauthenticated
  NZ-country leaderboard feed (`feeds/leaderboard/public/country/list_1_351_0_1.json`)
  is a static top-500-only snapshot — confirmed not a real paginated API
  (page 2 just 404s). Only managers who happen to rank in NZ's actual top
  500 will ever show an NZ rank; there's no way to get it for the rest
  without their personal session cookie, which isn't worth asking for. This
  is accepted, working-as-intended behavior, not a bug to keep chasing.
- **Sprint weekends don't get a separate "Sprint Race" points column** from
  F1's API — `SessionWisePoints` only ever has Sprint Qualifying/Qualifying/Race,
  and Race already includes both the sprint race and the main race combined
  (verified: they sum exactly to the known total). The UI relabels that
  column "Sprint + Race" on sprint weekends rather than fabricating a split
  that doesn't exist upstream.
- **A Wildcard week can leave a stale 8th pick** in the API response (a
  reversed-transfer artifact, confirmed live on Monaco). Code keeps the
  highest-numbered 7 picks rather than guessing which one is stale.

## Site structure (tabs, in order)

1. 🏁 Leaderboard — live/latest-race weekend summary box, Standings, points
   progression chart, Global Standing (merged in at the bottom — includes NZ
   rank where available, both with approximate percentiles since F1 doesn't
   expose exact global/NZ player counts, only "2.1m+" / "27.5k+" style
   figures from their own UI)
2. 🗓 Race Breakdown — Points per race (all managers, bar chart) above Round
   by Round (newest race first), Weekend Points Summary archive with a race
   picker
3. ⚔️ Head-to-Head
4. 💰 Budget Tracker
5. 🏆 Podiums — Podium Share (medal-dot pictogram) + Race Results (one row
   per finisher, CSS-grid based — see below for why not a real `<table>`)
6. 📊 Stats — Finish Distribution, Chip Usage, season highlights
7. 📈 Positions — Position Timeline only (Standings Movement table was
   removed as redundant — Position Timeline shows the same info better)
8. 🧩 Team Picks — Lineup Viewer (sorted by current-season price value,
   fixed 2-column top-to-bottom-then-left-to-right grid; shows each pick's
   price, price change on completed weekends, and a team total), Transfers,
   Transfer Impact Overview/per-Race (diverging bar charts, reuses the same
   trade-swing math as Trade Regrets/Best Trades), Driver/Constructor
   Popularity, Trade Regrets, Best Trades, Loyal Holds, DRS Performance
9. 🏎 Driver Results — **currently in local preview only, not yet approved
   for the live site** (see Pending below). Ranked by fantasy points per
   race (not DRS-doubled — this is *not* the same as F1's real official
   finishing order, which isn't data we have) with an "Owned by" column
   showing which manager(s) had each driver/constructor.

### Design system
- Dark theme: body `#0f0f0f`, cards `#1a1a1a`, borders `#2a2a2a`
- Chart.js 4.4.1 from cdnjs
- **Podium/Race-Results-style tables are CSS-grid rows, not real `<table>`
  elements.** A real `<table>` with `rowspan` (to visually merge a race's
  rows, or a tied position's rows) only draws its border under the *last*
  row of the span, leaving every continuation row's gridline broken/partial
  — and table-cell borders at 0.5px are also less reliable on mobile than a
  plain div border. The fix used everywhere now: one grid-row div per line,
  each with its own full-width `border-bottom`, with the "merged" look
  achieved by simply leaving the Race/Pos cell blank on continuation rows
  rather than real cell merging. `podium_table_html()` is the shared
  helper — Leaderboard's (now-removed, see Pending) Latest Podiums and
  Podiums page's Race Results both used it so they couldn't drift apart.
- Any horizontally-scrolling wide content needs its own `overflow-x:auto`
  wrapper with an explicit `min-width` on the *scrollable content*, not
  just the outer card — a `minmax(Xpx,1fr)` grid column with no scroll
  wrapper will happily blow out the whole page's width on mobile. This bit
  us multiple times (Global Standing, Standings Movement, Finish
  Distribution) before the pattern was made consistent.
- Custom scrollbar styling (dark, matching the theme) is global in
  `SHARED_CSS` — desktop browsers otherwise show a jarring light system
  scrollbar on the wide tables.

## How Tim likes to work (see also Claude's own memory system for more)

- **Never guess or fabricate data** — verify against a real live API call,
  or ask Tim to check/confirm from memory. This has come up repeatedly
  (Wildcard field, budget lag direction, tie handling, NZ leaderboard
  limits) and every one of those was resolved by actually querying the API
  live rather than assuming.
- **Only commit/push when explicitly asked.** For UI/feature work, the
  normal cycle is: build the change, generate the local scratchpad test
  file (not the real `index.html`), let Tim review on his phone, then ship
  once asked (or once he's clearly established the ship-then-test-live
  pattern for a run of related fixes).
- New pages/tabs get built as **local preview only** first (added to
  `PANELS` for the scratchpad test build, but commented back out of `PANELS`
  before anything gets committed/pushed) until Tim explicitly approves the
  format.
- Destructive-ish server actions (resetting the sentinel's git state,
  deleting a stale DB) are fine to just do and report, since they're
  reversible/safe by construction (sentinel makes no unique commits; DB is
  always re-fetchable) — but always verify the result (row counts, a real
  git log) rather than trusting a log line that says "OK".
